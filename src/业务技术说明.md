# 业务与技术说明

## 1. 系统定位

这套代码不是通用 RAG，而是面向“实景三维质检时空数据规范”的专用知识系统。核心目标有三类：

1. 对 7 份规范文档做结构化处理，保留章节、条款、表格和业务元数据。
2. 把规范条款、检查项字典统一写入 Milvus，支持高质量召回。
3. 面向用户提供三种能力：纯检索、全文总结、质检方案生成。

`src/` 这一层更像“阶段化业务外壳”，真正的语义提取、切块、召回和方案编排主要复用 `qualityScheme/` 里的成熟实现。

## 2. 业务主线

系统的业务对象是“时空数据规范”。语料来源于 `standard/` 下的 PDF，经过增强提取后落到 `src/data/`，再被切块、向量化、写入 Milvus。检查项清单保留在业务模块中供方案生成参考，但不再作为 Node 写入向量库。

最终，系统支持：

1. 用户问“某类数据该怎么查、怎么判”。
2. 用户问“这套规范讲了什么”。
3. 用户输入自然语言需求，系统自动生成结构化质检方案。

## 3. 数据处理

数据处理链路是这套系统最关键的一段，核心思想是“先去噪，再结构化，再切块”。

`qualityScheme/enhanced_extractor.py` 先从 PDF 中剔除目录、页眉、页码等噪声，再按章节编号解析出 `chapter_no`、`chapter_title`、`section_type`、`knowledge_type`、`data_name`、`field_name`、`param_hint` 等元数据，并把这些信息写进 Markdown 注释里。这样做的好处是：元数据在源头注入，后面切块时直接继承，不需要再猜。

`qualityScheme/smart_chunker.py` 再按章节路径分组，把同一章节的内容聚合成章节级 `Document`，随后使用 `SentenceSplitter(384/64)` 在章节内部细切。这里比默认 256/40 更适合中文规范，因为标准条款往往较短，但又不能把编号和正文切散。表格内容会尽量整块保留，避免语义被拆碎。

这一层的结果不是“纯文本”，而是带业务语义的文档块。它直接决定后面的召回质量。

## 4. 索引构建

索引构建聚焦规范文档本身：章节级 `Document` 会被切成带 metadata 的规范 `Node`。

`src/indexing.py` 会把章节级 `Document` 变成 `Node`，并按源 markdown 文件把切块结果导出到 `src/node/*.json`。这个目录用于人工审计切块文本、metadata 和顺序编号；embedding 不重复写入 JSON，避免本地派生产物过大。

`src/storing.py` 负责把规范 Node 写入 Milvus。它会先探测 embedding 维度，再确保数据库存在，然后创建 `MilvusVectorStore`。这里显式开启 `enable_sparse=True`，是为了支持 Hybrid 检索；相似度度量也统一设为 `COSINE`。写入完成后还会生成 `src/storage/src_manifest.json`，记录模型名、规范节点数和版本信息，用于启动时校验一致性。

启动时如果 Milvus 里已经有数据，`server.py` 会自动加载索引，避免重复重建。

## 5. 检索召回策略

召回不是单一向量检索，而是“元数据过滤 + Hybrid 检索 + 业务兜底”的组合。

`src/querying.py` 和 `qualityScheme/metadata_filter.py` 支持多字段过滤，包括 `part_number`、`file_name`、`knowledge_type`、`data_name`、`doc_type`、`section_type`、`chapter_no`、`check_code`。其中 `retrieve_by_part()` 会直接在 Milvus 侧做 `part_number` 精确过滤，避免先召回再内存筛选。

Hybrid 召回是重点：Dense 向量负责语义相近，BM25 稀疏向量负责编号、代号、阈值、字段名这类强关键词。对质检规范这种“编码密集型”语料，Hybrid 明显比纯向量更稳。

方案生成时还会走渐进式召回：优先检索 `quality_rule`，不够再扩到 `field_rule`，最后才放宽限制。这样能尽量把高价值条款排在前面。

## 6. 查询优化

查询优化主要体现在三件事上：

1. `QueryEngine` 默认使用 `compact` 合成模式，普通问答快；需要长文总结时再切 `tree_summarize`。
2. `streaming=True` 支持流式输出，Web 场景下可以减少“长时间无响应”的体感。
3. 方案生成不是直接让 LLM 面对 28 项检查项，而是先做 Query Decomposition，把复合需求拆成多个子意图，再分别检索候选检查项和规范上下文，最后只允许从候选白名单里出方案。

另外，`src/summary.py` 做了两级缓存：同样的问题直接复用答案，不同问题但同一批语料时复用切块结果，减少重复计算。

## 7. 基础设施

基础设施层主要由 `src/server.py` 和 `src/state.py` 负责。

服务启动时只加载配置和模型，不主动建索引；如果检测到 Milvus 已有数据，会自动加载索引。整个流程用 `RuntimeState` 保存 `config`、`llm`、`embed_model`、`documents`、`nodes`、`index` 和阶段状态，避免每个请求重复初始化重对象。构建索引、写库、总结这类耗时操作都通过 `asyncio.to_thread()` 放到线程池，避免阻塞 FastAPI 事件循环。

系统提供了分阶段 API：`/api/loading`、`/api/indexing`、`/api/storing`、`/api/querying`，也保留了问答、总结、流式、方案生成和一键重建接口。前端静态页面挂载在 `src/static/`，用于展示流程状态和调用结果。

## 8. 一句话总结

这套系统的本质，是把“规范文档 + 检查项字典”做成一个可分层召回的质检知识库：数据处理负责提纯语料，索引构建负责沉淀知识，召回策略负责找准候选，查询优化负责让 LLM 少走弯路，基础设施负责让整条链路稳定可用。
